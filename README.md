# 퍼스널 컬러 & 코디 진단 서비스

사진(또는 영상)에서 **퍼스널 컬러 12타입**을 추정하고, 전신 사진으로 **체형·비율·얼굴형**을
분석해 **코디 · 헤어스타일 · 헤어컬러 · 메이크업**까지 추천하는 서비스입니다.
추천한 색과 아이템은 **가상 피팅**으로 자기 전신 사진에 직접 입혀 볼 수 있습니다.

> **자동 진단기가 아니라 "사진 기반 퍼스널 스타일 가이드"입니다.** 전문가 판정과의 일치율은
> 검증되지 않았습니다. 무엇을 믿어도 되는지는 [이 도구의 정확한 포지션](#이-도구의-정확한-포지션)을 보세요.

## 서비스 흐름

```
0 온보딩 (화장·염색 여부, 촬영 가이드)
   ↓
1 바스트샷 (사진 1장 · 사진 2~3장 · 3~5초 영상)
   → 품질 게이트 → 예비 색캐스트 제거 → 얼굴/부위 검출
   → 화이트밸런스 확정 → 사용자 보정(드래그)
   ↓
2 퍼스널 컬러 결과  ← 여기서 이미 완결된 서비스
   3축 좌표 · 12타입 적합도 · 팔레트 조화 예측 · 재현성 · 촬영품질/구분도 · 판정 근거
   → 비교형 진단(선택) : 색 쌍 6문항을 직접 골라 자동 판정과 대조
   ↓
3 전신샷 (선택)  정면 1장 (+ 좌·우 옆모습 2장)
   → 체형 5분류 · 핏 성향 3분류 · 얼굴형 · 비율
   → 옆모습이 있으면 : 앞뒤 두께 측정 → 둘레 추정 → 옷이 몸을 감싸는 모양
   → 실측 입력(선택) : 키·둘레로 별도 판정해 사진 결과 검산
   ↓
4 종합 리포트  색 배치 전략 · TPO 코디 5종 · 헤어 · 메이크업 · 액세서리
   → 가상 피팅 : 추천 색·아이템을 전신 사진에 직접 입혀 보기
   ↓
5 저장 / 공유 (PDF · JSON · 피팅 이미지)
```

## 핵심 설계

### 1. 모든 색 연산은 CIELAB에서
sRGB는 지각적으로 균일하지 않습니다. 선형화 → XYZ(D65) → CIELAB 변환 후 계산하며,
색차는 ΔE2000(Sharma 정의)을 씁니다.

### 2. 화이트밸런스를 가장 먼저 푼다
> 백열등 아래서 찍으면 누구나 웜톤으로 나옵니다. 이 문제를 못 풀면 서비스 전체가 무의미합니다.

3단 방어선을 씁니다.

1. **예비 색캐스트 제거** — *피부 검출보다 먼저.* 웜 조명에서는 회색 벽·나무·베이지 옷이
   전부 피부 색 규칙을 통과해서, 보정 없이 검출하면 배경이 통째로 "얼굴"이 됩니다.
2. **공막(눈 흰자) 앵커** — 비교적 중성에 가까워 임시 기준점으로 쓸 만합니다(절대 기준은 아닙니다).
3. **무채색 면 추정 / 전역 추정** — 공막이 과노출로 날아갔을 때의 대체 수단.

그리고 **복원 불가능한 사진은 거부합니다.** 얼굴의 특정 채널이 날아간(클리핑) 사진에는
언더톤 판정에 쓸 색 정보가 남아있지 않으므로, 그럴듯한 오진 대신 재촬영을 요구합니다.

### 3. 블랙박스를 쓰지 않는다
딥러닝 단일 분류기 대신 **3축 연속 점수 → 12타입 거리 → 적합도** 방식을 씁니다.

```
warm   : 피부 색상각 h° · b* · 황적비 · 모발 · 입술
light  : ITA° · 피부 명도 · 모발 명도
bright : 명도 대비 · 피부 채도 · 균일도 · 홍채 선명도
```

덕분에 *"피부 색상각이 62°로 노란기가 우세하고 모발-피부 대비가 낮아 봄 라이트에 가깝습니다"*
같은 **근거 문장을 자동 생성**할 수 있습니다.

### 4. 팔레트 조화 예측 + 직접 대보기
오프라인 컬러리스트가 보는 6가지 관찰 항목(안색 맑음 · 홍조 억제 · 그림자 완화 ·
윤곽 리프팅 · 눈동자 또렷함 · 주객 균형)을 3축 좌표에서 **예측**하고,
실제로 **얼굴 아래에 색을 합성해 눈으로 비교**할 수 있게 합니다.
예측 점수는 같은 축에서 다시 계산한 값이라 독립 검증이 아닙니다 — 눈으로 본 쪽이 우선입니다.

### 5. 확실성을 **두 개로 쪼개서** 낸다

예전 버전은 촬영 품질과 타입 구분도를 곱해 **"신뢰도 82%"** 하나로 표시했습니다.
이 값은 전문가 판정과의 일치율이 아닌데도 정확도처럼 읽혀서, 사용자가 결과를
과신하게 만드는 표현이었습니다. 지금은 성격이 다른 두 값을 분리해서 보여줍니다.

| 표시 | 뜻 | 뜻하지 않는 것 |
|---|---|---|
| **촬영 품질** 좋음/보통/낮음 | 이 사진에서 색을 얼마나 믿고 읽을 수 있는가 | 정답률 |
| **결과 구분도** 뚜렷함/보통/경계형 | 1위와 2위 타입이 얼마나 벌어져 있는가 | 1위가 맞을 확률 |

12타입 옆의 숫자도 **확률이 아니라 이 모델 안에서의 상대 적합도**입니다.
전문가 기준 정확도는 **아직 검증 전**이며, 결과 화면 맨 위에 그 사실을 명시합니다.

### 6. 얼굴을 22곳에서 잰다

측정 지점이 적으면 그중 **하나만 오염돼도** 피부색 추정이 통째로 밀립니다. 실제 얼굴에는
잡티·그림자·볼터치·흘러내린 머리카락이 반드시 섞입니다.

**눈 사이 거리(IOD)를 기준자로 쓰는 얼굴 좌표계**를 세우고, 그 위에 22개 영역을 배치합니다.
얼굴 박스는 머리 길이·조명·배경에 따라 흔들리지만 눈 사이 거리는 안정적이며,
두 눈을 잇는 선에서 **머리 기울기(roll)까지 함께 보정**됩니다.

```
가로 단위 = IOD                       세로 단위 = (턱 − 눈높이) / 1.45
이마 3 · 관자놀이 2 · 눈밑 2 · 볼 6 · 코 3 · 턱선 2 · 턱 1 · 목 1 · 입술 1 · 눈썹 2
```

수집한 뒤에는 **중앙값에서 색차가 큰 지점을 두 차례 걸러냅니다.** 임계값은 고정값이 아니라
MAD(중앙값 절대편차) 기반으로 데이터에 맞춰 정합니다 — 고정값은 조명에 따라 과·소검출됩니다.
고개가 돌아갔으면(yaw) 멀어진 쪽 볼의 가중치를 낮춥니다.

사용자는 22개 점을 하나씩 옮기지 않습니다. **양쪽 눈과 턱 3개 핸들**만 잡으면
나머지가 얼굴 계측 비율대로 따라옵니다.

### 7. 결과는 읽는 게 아니라 만지는 것

진단 결과가 지루해지는 원인은 **세로로 긴 텍스트와 표**이고, 사용자가 할 수 있는 행동이
스크롤뿐이라는 점입니다. 네 가지로 풀었습니다.

| 문제 | 해결 |
|---|---|
| 만질 게 없다 | **드레이핑 스튜디오** — 색을 누르거나 마우스만 올려도 즉시 내 얼굴에 대본다<br>**A/B 슬라이더** — 최고색과 최악색을 손잡이로 밀어가며 비교 |
| 글자뿐이다 | **코디 SVG 일러스트** — 착장을 그림으로<br>**헤어 염색 미리보기** — 실제 모발 픽셀을 추천 색으로 치환<br>**타입 좌표 맵** — 12타입 중 내 위치<br>**공유 카드** — 9:16 이미지 저장 |
| 한 페이지가 너무 길다 | **탭 분리**(코디 / 색 배치 / 헤어 / 뷰티 / 저장) + 수치는 접어두기 |
| 결과가 툭 튀어나온다 | **리빌 연출** · 숫자 카운트업 · 게이지 채우기 · 레이더 그려지기 · 스크롤 등장 |

모션은 전부 `prefers-reduced-motion`을 존중하며, 등장 애니메이션이 어떤 이유로든 실패해도
**콘텐츠가 영구히 숨겨지지 않도록** 3중 안전망(즉시 표시 → 관찰자 → 타이머)을 두었습니다.

### 8. 얼굴 근접부에 가중치
실제 조화는 얼굴 반사광에서 결정됩니다. 상의·스카프·헤어컬러는 팔레트를 엄격히,
하의·신발은 자유도를 높게 잡습니다.

### 9. 코디는 읽는 것이 아니라 입어 보는 것

색 이름과 아이템 목록만으로는 사용자가 상상해야 합니다. **가상 피팅** 탭은
진단된 팔레트의 색을 **자기 전신 사진에 실제로 얹어서** 보여줍니다.

상용 가상 피팅(VITON-HD · IDM-VTON 계열)의 순서를 그대로 따르되,
마지막 **생성 모델 다듬기** 단계만 물리적 규칙으로 대체했습니다.

```
① 원래 옷 지우기 → ② TPS 부위별 워핑 → ③ 합성 → ④ 생성 모델 다듬기
                                                    ↑ 이 단계만 대체
```

④가 GPU 서버와 수 GB 가중치를 요구하는 유일한 단계이고, 그것을 넣으면
**사진을 서버로 보내야 하기 때문**입니다. P1 검출 개선에서 모델 도입을
미룬 것과 같은 판단입니다.

생성 모델 없이 합성이 "붙여넣기"로 보이지 않게 하는 것은 결국 빛입니다.
사진을 크게 흐려 **조명장**을 뽑고 옷에 다시 곱합니다 — 왼쪽에서 빛이 든
사진이면 옷의 왼쪽도 밝아집니다.

| | 내용 |
|---|---|
| **옷 DB** | 8스타일 × 4부위 **45벌**. 실루엣 + 소재별 직조 + 드레이프 주름 + 정반사를 합성한 래스터 |
| **내 옷 반입** | 상품컷을 넣으면 배경 자동 제거 · 앵커 추정 후 IndexedDB에 저장 (브라우저 밖으로 나가지 않음) |
| **색 변환** | 픽셀을 `옷 색 × 닿은 빛`으로 분해해 색 성분만 교체. 소재별로 광택·채도 곡선이 다름 |
| **되재기** | 목표색 오차 ΔE · 질감 보존 %를 화면에 그대로 표시 |

**실제 상품컷을 담을 수 없는 이유는 기술이 아니라 권리입니다.** 쇼핑몰
상품컷은 저작물이고, 공개 데이터셋(VITON-HD · DressCode · DeepFashion)은
연구 목적 라이선스라 배포본에 담을 수 없습니다. 그래서 옷을 **그리지 않고
합성하고**, 실제 사진은 사용자가 직접 넣게 했습니다.

자세한 내용과 구현 중 발견한 실패들은
[6. 가상 피팅 원리와 구현](docs/06_가상피팅_원리와_구현.md)에 있습니다.

### 10. 옆모습 두 장이면 앞뒤 두께를 **잰다**

이 도구가 스스로 적어 둔 가장 큰 한계는 *"정면 한 장에서 몸의 3D 형태를 알 수
없다"* 였습니다. 3단계에서 **좌·우 옆모습**을 더 받으면 이 한계가 사라집니다.

몸통 단면의 반폭 `a`(좌우)·반두께 `b`(앞뒤)에 대해, θ만큼 돌아선 실루엣 반폭은
`w(θ)=√(a²cos²θ+b²sin²θ)` 입니다. 정면이 `a`를 주고, **옆모습(θ=90°)이 `b`를
그대로 줍니다.**

> 처음에는 45°씩 좌우로 돌린 두 장으로 각도와 두께를 함께 풀려 했습니다.
> 실측에서 각도가 늘 탐색 상한에 눌러앉아 알았습니다 — **좌우 대칭으로 돌면
> 어떤 각도를 넣어도 좌우가 똑같이 맞습니다.** 두 사진의 일치는 각도에 대해
> 아무 정보도 주지 않습니다(1-매개변수 축퇴).

옆모습을 쓰는 이유는 두 가지입니다.

1. **각도에 둔감합니다.** θ=90°에서 `dw/dθ = 0` 이라, 80°로만 돌아서도
   두께 오차가 3 %입니다. 정확히 맞추라고 요구하는 대신 **둔감한 지점에서**
   잽니다.
2. **단면 모양과 무관합니다.** θ=90°에서는 어떤 단면이든 `w = b` 입니다.
   단면을 타원이 아닌 초타원으로 그려 시험해도 오차가 **똑같이 2.7 %** 였습니다.
   타원 가정은 두께를 *둘레*로 바꿀 때만 들어옵니다.

그러면 좌우 두 장은 왜 받는가 — **검산하기 위해서**입니다. 같은 몸통이니
왼쪽에서 잰 두께와 오른쪽에서 잰 두께는 같아야 합니다. 벌어지면 자세가
틀어진 것이고, 그 사실을 보고합니다.

| 조건 | 두께 오차 | 둘레 오차 (가슴/허리/골반) |
|---|---|---|
| 옆모습 90° | **2.7 %** | +1.1 / +2.1 / −2.5 cm |
| 80° (덜 돌아섬) | 3.1 % | +1.1 / +2.1 / −3.3 cm |
| 초타원 단면 | 2.7 % (동일) | 동일 |
| 좌우 비대칭(90/72°) | 3.3 % | 좌우 편차 12 % 감지 |

안내를 어기고 **45°만 돌아선 사진**은 두께를 크게 부풀립니다. 이건 **머리**로
잡아냅니다 — 두개지수(앞뒤/좌우 ≈ 1.28)는 몸통 비율보다 사람 사이 편차가
훨씬 작아서, 머리 폭의 정면 대비 비가 90°에서 1.28, 45°에서 1.15로 뚜렷이
갈립니다. 시험에서 45° 컷이 *"약 41°"* 로 읽혀 경고가 떴습니다.

잰 값은 세 곳에 쓰입니다.

- **원통 감기** — 옷이 몸 앞에 납작하게 붙는 대신 실제 단면을 따라 감깁니다.
- **세 시점 피팅** — 정면·왼쪽·오른쪽에 같은 착장을 입혀 보고 전환합니다.
- **핏을 cm로** — "적당합니다 · 여유 +8cm" 처럼 여유분을 숫자로 말합니다.

자세한 내용과 이 과정에서 두 번 틀린 핏 계산의 기록은
[7. 다각도 촬영과 앞뒤 두께](docs/07_다각도_촬영과_앞뒤두께.md)에 있습니다.

### 옷을 붙이기 전에 — 몸을 제대로 읽는다

첫 결과를 보고 사용자가 한 말은 "찢어진 천을 붙힌 수준"이었습니다. 원인은
옷을 그리는 쪽이 아니라 **몸을 읽는 쪽**이었습니다.

- **인물 분리**를 합성 해상도에서 다시 합니다. 임계는 배경 자신의 산포에서
  정합니다 — 옷과 배경이 같은 색일 때 IoU가 0.33 → 0.86, 0.17 → 0.87로
  올랐습니다.
- **어깨·허리·골반을 얼굴 없이** 실루엣 폭 프로파일에서 찾습니다. 반팔
  사진에서는 두 팔이 얼굴보다 큰 살색 덩어리라, 얼굴 기반 검출이 어깨를
  440(정답 174)으로 잡고 있었습니다.
- 잰 값이 약할 때는 **버리지 않고 해부학 비율 쪽으로 끌어당깁니다** —
  옆선이 밋밋한 사람의 허리처럼, 최솟값의 위치를 잡음이 정하는 경우입니다.

자세한 기록은
[8. 인물 분리와 랜드마크](docs/08_인물_분리와_랜드마크.md)에 있습니다.

원본이 바뀌었는데 조용히 잘못 합쳐지는 일을 막습니다.

```bash
node build/test-tryon.mjs   # 워핑 품질 지표 (비단조 구간 · 매핑 이탈률)

node build/test-multiview.mjs  # 정답을 아는 합성 인물로 두께 측정 정확도
```

`web/index.html`을 직접 열면 브라우저의 `file://` 제약으로 스크립트가 로드되지 않을 수

## 이 도구의 정확한 포지션

> **자동 진단기가 아니라 "사진 기반 퍼스널 스타일 가이드"입니다.**

무엇을 믿어도 되고 무엇은 아닌지 솔직하게 적습니다.

| 영역 | 실용성 | 진단으로서의 신뢰도 |
|---|---|---|
| 팔레트 탐색 · 직접 대보기 | 높음 | — (도구이지 판정이 아님) |
| 가상 피팅으로 색 확인 | 높음 | — (도구이지 판정이 아님) |
| 앞뒤 두께 측정 (옆모습 2장) | 높음 | **중간~높음** (합성 기준 오차 2.7%) |
| 둘레 추정 (키 입력 필요) | 중간 | 중간 — 단면 타원 가정이 들어감 |
| 가상 피팅의 실제 착용 재현 | 낮음 | **낮음** |
| 사진 품질 점검 · 측정점 확인 | 높음 | 중간 |
| 12타입 자동 판정 | 중간 | **낮음~중간 (검증 전)** |
| 체형·비율 추정 | 제한적 | **낮음** |
| 핏 성향(스트레이트/웨이브/내추럴) | 낮음 | **매우 낮음** |
| 코디·헤어 아이디어 | 높음 | 판정이 맞다는 전제 필요 |

### 왜 그런가

**1. 사진의 RGB는 그 사람의 피부색이 아닙니다.**
조명 색온도, 스마트폰 자동 화이트밸런스, HDR·톤매핑, 기종별 피부 보정, 필터, 노출,
JPEG 압축, 메이크업이 전부 섞인 결과입니다. 이 코드는 그중 조명색을 걷어내려 하지만
사진 한 장으로 조명과 피부를 완전히 분리할 수는 없습니다.

**2. 공막(눈 흰자)은 그레이카드가 아닙니다.**
비교적 중성에 가깝지만 혈관·건조·황색도·눈꺼풀 그림자의 영향을 받고 면적이 작아 오차가 큽니다.
"흰 옷·흰 벽"도 진짜 중성 흰색인지 알 수 없습니다(아이보리 옷, 웜화이트 벽). **보조 기준일 뿐입니다.**

**3. 웜/쿨 기준값은 휴리스틱입니다.**
색상각 57°, b* 16.5, 황/적 1.65 같은 중심값은 **개발자가 설계한 값**이며 라벨 데이터로
학습하거나 임상 검증한 값이 아닙니다. 계산이 정교한 것과 결과가 전문가 판정에 맞는 것은
별개의 문제입니다.

**4. 팔레트 조화 예측은 독립 검증이 아닙니다.**
이름을 "가상 드레이핑 검증"에서 바꾼 이유입니다. 색을 얼굴에 합성한 뒤 실제 픽셀 변화를
측정하는 것이 아니라, 이미 계산한 3축 좌표에서 다시 점수를 매기는 것이라 **같은 판정의
재점수화**에 가깝습니다. 화면의 "직접 대보기"에서 눈으로 비교한 결과가 더 믿을 만합니다.

**5. 체형은 몸이 아니라 사진 속 실루엣을 잰 것입니다.**
옷 두께·핏, 팔 위치, 카메라 높이와 렌즈 왜곡, 몸의 회전, 자세가 폭과 비율을 크게 바꿉니다.
특히 스트레이트/웨이브/내추럴은 뼈·관절·몸의 앞뒤 두께를 봐야 하므로 정면 사진 한 장으로는
확정할 수 없습니다. 그래서 **"핏 성향 추정"** 으로만 씁니다.

### 그 밖의 한계

- 자동 검출은 초안입니다. 눈·턱 핸들과 체형 가이드 라인을 **직접 보정**하게 만든 이유입니다.
- 화장·염색은 타고난 색을 가립니다. 온보딩 정보로 가중치를 조정하지만 완전히 상쇄되지는 않습니다.
- 피부 검출이 고정 임계값 기반입니다. 공정성은 **합성 이미지로만** 확인했습니다 —
  밝은/중간/어두운 피부톤 × 밝은/어두운 배경에서 오탐 0건, 어두운 피부톤의 신뢰도가
  밝은 피부톤보다 낮아지지 않는 것을 테스트로 고정했습니다(저노출 판정에 평균 밝기 대신
  상위 분위수를 쓰는 이유도 이것입니다). **실제 사람 사진으로는 검증하지 못했습니다.**
- 전신 분석은 단색 배경에서 가장 정확합니다. 가상 피팅도 같은 인물 마스크를
  쓰므로, 옷과 배경 색이 비슷하면(흰옷 + 흰벽) 덮이는 면적이 크게 줄어듭니다.
- 가상 피팅에서 원래 옷이 새 옷보다 크면 드러나는 부분을 **복원할 수 없고**,
  주변 색으로 메운 뒤 그 면적을 화면에 보고합니다. 팔짱처럼 복잡한 가림은
  처리하지 못합니다.
- 앞뒤 두께는 **잰 값**이지만 둘레는 단면을 타원으로 가정해 **환산한 값**입니다.
  실제 허리 단면은 타원보다 각져 있어 대체로 작게 나옵니다 — 줄자로 한 곳만
  재서 넣으면 그 비율로 나머지를 보정합니다. 사진 속 몸 둘레에는 그때 입고
  있던 옷 두께가 포함됩니다.
- 옆모습이 없으면 앞뒤 두께를 표준 비율(폭의 72%)로 **가정**하며, 화면에
  그것이 가정임을 밝힙니다.

### 재현성 측정 — 검증 데이터 없이도 참인 유일한 지표 ✅

사진 한 장에 점수를 붙이는 것보다 **여러 입력에서 같은 답이 나오는가**가 훨씬 강한 근거입니다.
모델이 매긴 점수와 달리, "3장 중 3장에서 봄 계열"은 **실제로 관측된 사실**이라 검증 없이도 참입니다.

**사진을 2~3장 함께 올리거나 영상을 올리면** 각각을 독립적으로 진단해 다음을 보여줍니다.

- 입력별 판정 결과 (다수와 다른 입력은 `≠` 로 표시)
- 계절 일치율 · 12타입 일치율
- 축별 흔들림 (웜/밝기/맑기의 표준편차)

그리고 **불일치가 관측되면 모델의 자체 구분도를 무시하고 강등합니다.** 한 장에서 아무리
깔끔하게 갈려도 다른 장에서 다른 답이 나오면 그 판정은 확정하면 안 되기 때문입니다.

| 일치율 | 표시 | 결과 처리 |
|---|---|---|
| 계절 85%+ & 타입 60%+ | 안정적 | 그대로 |
| 계절 70%+ | 대체로 일치 | 구분도 강등, "계절까지만 확정적으로" |
| 계절 70% 미만 | 불일치 | **"입력마다 다름"으로 강등, 확정 중단** |

> 색 통합에는 품질 상위 절반만 쓰지만, **재현성은 성공한 입력 전부**로 잽니다.
> 잘 맞은 것끼리만 비교하면 일치율이 부풀려집니다.


## P2 검증 데이터 — 왜 막혔고, 대신 무엇을 했는가

"실제 사진과 전문가 라벨이 없다"는 말은 문제를 절반만 설명합니다. 사진을 모아도
풀리지 않는 부분이 남습니다.

### 막힌 이유 세 겹

**1. 정답이 존재하지 않습니다 (오라클 문제).**
"이 사진에 고양이가 있는가"는 정답이 있습니다. "이 사람이 봄 웜인가"는 없습니다.
퍼스널 컬러는 물리적 사실이 아니라 **유파의 판단 체계**입니다. 4계절·12타입·
Sci\ART·먼셀 기반이 서로 다른 경계를 씁니다. 전문가 1000명의 라벨을 모아도 얻는 것은
"정답과의 일치율"이 아니라 **"특정 유파와의 일치율"** 입니다. 이건 데이터를 더 모아서
해결되는 종류의 문제가 아닙니다.

**2. 라벨을 사진에 붙이면 대상이 바뀝니다.**
전문가는 통제된 조명 아래에서 실물 천을 대보며 판정합니다. 사진을 보여주고 라벨을
받으면 그 전문가는 **사람이 아니라 사진을 판정**한 것입니다. 그렇게 만든 데이터셋으로
검증되는 것은 "이 사람의 타입을 맞히는가"가 아니라 "이 사진에 대해 전문가가 할 말을
예측하는가"입니다. 다른 과제이고, 더 약한 과제입니다.

**3. 실물 진단을 라벨로 쓰면 사진과 짝이 맞지 않습니다.**
오프라인에서 받은 진단 결과를 라벨로 쓰면 (2)는 피하지만, 그 진단은 우리가 받은 사진과
다른 조명·다른 날의 얼굴에 대해 내려진 것입니다. 짝이 어긋난 라벨입니다.

세 겹 모두 **코드로 풀 수 없습니다.** 데이터 수집·동의·보상, 그리고 어느 유파를
기준으로 삼을지에 대한 사업적 결정이 필요합니다.

### 그래서 무엇을 대신했는가 — 정답 없이 잴 수 있는 것들

정확도를 잴 수 없다고 해서 아무것도 잴 수 없는 것은 아닙니다. **정답을 몰라도 참인
성질**이 있고, 그것들은 정확도의 필요조건입니다.

| 대체 지표 | 정답 없이 성립하는 이유 | 실측값 |
|---|---|---|
| **재현성** | "7장 중 6장에서 봄"은 라벨 없이도 참 | 구현 완료 |
| **변형 불변성** | 같은 사람인데 조명만 바꿔 답이 달라지면 안 된다 | 주광 D50~D75 **9/9 유지** |
| **조용한 오답 0건** | 답이 바뀌었으면 스스로 낮게 표시해야 한다 | **0건** (수정 전 2건) |
| **단조성** | 노란기를 올리면 웜 축은 반드시 올라가야 한다 | 웜·밝기 축 모두 단조 |
| **순서 보존** | 명백히 더 웜한 쪽이 더 웜하게 나와야 한다 | 0.88 > 0.29 > −0.79 |
| **결정 여유** | 경계까지의 거리는 정답을 몰라도 잴 수 있다 | ΔE 단위로 화면 표시 |
| **비교형 진단** | 사용자 본인의 관측을 근거로 투입 | 구현 완료 |
| **실측 검산** | 줄자는 관측이지 추정이 아니다 | 구현 완료 |

이것을 **변형 검사(metamorphic testing)** 라고 합니다. 오라클이 없는 시스템을 검증하는
표준적인 방법입니다. 재는 것은 정확도가 아니라 **일관성**이지만, 일관성은 정확도의
필요조건입니다 — 조명 하나에 답이 바뀌는 엔진은 정답 라벨이 생겨도 맞을 수 없습니다.

### 결정 여유 (Decision Margin)

`"이 판정이 맞는가"`는 답할 수 없지만 `"이 판정이 얼마나 아슬아슬한가"`는 답할 수
있습니다. 얼굴색을 Lab 공간 14방향으로 밀어 보며 **계절 판정이 뒤집히는 최소 거리**를
ΔE2000으로 잽니다. 모델이 스스로 매긴 확률이 아니라 결정 경계까지의 실제 거리입니다.

```
전형적 웜    봄 스트롱   → 계절 여유 ΔE 6.5   보통
전형적 쿨    여름 브라이트 → 계절 여유 ΔE 4.2   보통
어두운 피부  가을 딥      → 계절 여유 ΔE 1.0   아슬아슬함
중성 애매    봄 라이트    → 계절 여유 ΔE 3.0   좁음
```

컬러 체커 카드를 쓰면 보정 잔차가 ΔE 0.5 안팎이지만 카드 없이 추정만으로 보정하면
잔차가 훨씬 큽니다. **여유가 그 잔차보다 작다면 그 판정은 조명 하나에 뒤집히는
판정입니다.** 계산은 1인당 약 30ms라 결과 화면에 바로 띄웁니다.

### 이 과정에서 찾은 공정성 버그

변형 검사가 실제 버그를 잡았습니다.

형광등 F11(4000K) 아래에서 **밝은·중간 피부는 거부**되는데 **어두운 피부는 신뢰도
0.93으로 오답**을 냈습니다. 원인은 클리핑 게이트였습니다 — 강한 조명색은 밝은 피부에서
먼저 채널을 날려 경보를 울리지만, 어두운 피부는 같은 조명에서도 클리핑이 생기지 않아
경보를 통과합니다. **색은 똑같이 망가졌는데 한쪽만 보호받고 있었습니다.**

수정: 보정 **전** 조명 왜곡(`preCast`)에도 감점과 경고를 붙였습니다. 이 지표는 피부가
아니라 빛을 재므로 피부톤과 무관합니다 — 같은 D50 조명에서 네 가지 피부톤 모두
0.115±0.001로 나옵니다. 임계값 0.18은 주광 실측 최대(0.116)와 백열등·형광등
최소(0.231) 사이에서 잡았습니다.

결과: 조용한 오답 **2건 → 0건**, F11 신뢰도 **0.93 → 0.68**, 주광 9/9 유지는 그대로.

### 남은 사실 하나 — 프로토타입 격자의 편향

정상 조명·무경고 조건에서도 신뢰도가 피부톤에 따라 벌어집니다.

```
밝은 0.97 · 중간 0.95 · 어두운 0.92 · 매우 어두운 0.66
```

촬영 품질은 네 경우 모두 "좋음"이고 검출도 전부 성공합니다. 격차는 전부
**구분도(separability)** 에서 나옵니다 — 어두운 피부톤이 놓이는 자리에서 12타입
프로토타입 격자가 성깁니다. 결정 여유가 ΔE 1.0으로 나오는 것과 같은 현상입니다.

**이건 라벨 없이는 고칠 수 없습니다.** 프로토타입 좌표를 옮기려면 "그 자리의 정답이
무엇인지"를 알아야 하는데, 그것이 바로 없는 데이터입니다. 지금 할 수 있는 일은
고치는 것이 아니라 **드러내는 것**이고, 그래서 판정 여유를 화면에 띄웁니다.

### 실제로 데이터를 모으려면 (코드 밖의 계획)

1. **사진을 모으지 않고 라벨만 모읍니다.** 이미 오프라인 진단을 받은 사용자가 그
   결과를 입력하면, 그 자리에서 대조 결과를 돌려받습니다(사용자에게 즉시 이득).
   전송되는 것은 사진이 아니라 *측정 수치 + 라벨* 뿐이라 프라이버시 약속이 유지됩니다.
2. **유파를 먼저 고정합니다.** 어느 체계를 기준으로 삼을지 정하지 않으면 일치율은
   해석 불가능한 숫자가 됩니다.
3. **경계 라벨을 버리지 않습니다.** 전문가 2~3인이 갈린 사례는 오답이 아니라
   *경계형*이라는 정보입니다. 우리 모델의 "결정 여유 좁음"과 대조하면, 정확도 없이도
   **경계 판정 능력**을 검증할 수 있습니다.
4. **1차 목표를 계절(4분류)로 낮춥니다.** 12타입 일치율은 전문가끼리도 낮습니다.

### 촬영 표준화 (구현 완료)

사후 보정에는 한계가 있습니다. 한쪽 채널이 날아간 사진은 어떤 알고리즘으로도
되살릴 수 없습니다. 그래서 **찍기 전에** 고치게 합니다.

**화면 내 촬영** — 얼굴 가이드 타원 위에 실시간 코칭 7항목(얼굴 크기 · 눈 인식 ·
정면·수평 · 초점 · 노출 · 좌우 조명 · 조명 색)을 초당 3회 판정하고, **전부 통과하기
전에는 셔터가 잠깁니다.** 각 항목은 문제가 아니라 조치를 말합니다("조금 더 가까이").
지원 기기에서는 화이트밸런스·노출을 수동 고정해 3연사 간 흔들림을 줄입니다.
자동 3연사는 그대로 재현성 측정의 입력이 됩니다.

> 저노출 판정에 **평균 밝기가 아니라 상위 분위수(p95)** 를 씁니다.
> 평균을 쓰면 어두운 피부톤이 "노출 부족"으로 오판됩니다. 어떤 피부톤이든
> 정상 노출이면 이마·코의 하이라이트가 존재하므로, 그 상단이 낮다는 것은
> 피부색이 아니라 노출 부족의 증거입니다.

**컬러 체커 카드 (정밀 모드)** — 회색 5 · 피부 3 · 유채색 4 = 12패치 카드를 인쇄해
얼굴 옆에서 함께 찍으면, 화이트밸런스가 **추정에서 계산으로** 바뀝니다.
선형 RGB에서 최소자승으로 3×3 보정 행렬을 풀고(클리핑된 패치는 제외, 릿지 정규화),
잔차 ΔE로 보정 품질 자체를 보고합니다. 합성 테스트에서 강한 색캐스트 기준
**평균 ΔE 8.64 → 0.48**, 피부 패치 ΔE 0.00입니다.

### 얼굴 위치 교차검증 (구현 완료)

얼굴 박스는 전적으로 **피부색 규칙**에서 나옵니다. 그래서 살구빛 벽·나무 가구·
베이지 옷처럼 피부와 색이 겹치는 것에 속고, **속아도 그럴듯한 결과를 계속
내놓습니다.** 정답을 아는 적대 장면을 직접 만들어 재보니 실제로 그랬습니다.

| 장면 | 이전 | 지금 |
|---|---|---|
| 정상 6장 (피부톤 3단계 × 배경 밝기) | 경고 0 · 신뢰도 0.98 | **그대로** (오탐 0) |
| 눈높이에 피부색 면이 맞닿음 | 폭 **120% 오차**인데 신뢰도 0.98 | 경고 3건 · 신뢰도 0.44 |
| 베이지 옷 + 베이지 벽 | 무성 실패 · 0.98 | 경고 · 0.55 |
| 어두운 피부 + 살구빛 벽 | 폭 120% 오차 · 무성 실패 | 경고 2건 · 0.34 |

핵심은 **정확히 맞히게 만든 것이 아니라, 틀렸을 때 틀렸다고 말하게 만든 것**입니다.
얼굴 박스는 피부 *색*에서, 눈은 *명암 구조*에서 나오는 서로 독립적인 근거이므로,
둘이 어긋나면 둘 중 하나가 틀린 것입니다.

> **비율은 이 오류를 못 잡습니다.** 박스가 부풀면 눈 탐색 창도 같이 부풀어
> 화면 양 끝의 엉뚱한 지점이 "두 눈"으로 잡힙니다. 분자와 분모가 함께 커지므로
> `폭 ÷ 눈간격` 은 **1.98 — 완벽한 정상값**이 됩니다. 실제 폭 오차는 120%인데도
> 비율 검사는 통과합니다.
>
> 잡히는 것은 **절대 크기**뿐입니다. 성인의 동공간거리는 얼굴 폭의 약 1/2.6이므로,
> 눈 간격이 화면 폭의 34%를 넘으면 얼굴이 화면보다 넓다는 뜻이 되어 성립하지
> 않습니다. 이 장면의 실측값은 **50.5%** 였습니다. (정상 사진 17~18%)

걸리면 눈을 **버립니다.** 틀린 눈은 없는 눈보다 나쁩니다 — 공막 화이트밸런스
기준점과 22개 측정점이 전부 그 위에 세워지기 때문입니다.

### 시도했다가 버린 것 — Haar 유사 얼굴 검증기

명암 배치(눈<뺨, 콧대>눈, 이마>눈, 좌우대칭)를 적분영상 위에서 재는 검증기를
만들어 봤습니다. 모델 파일도 학습도 필요 없어 매력적이었지만 **폐기했습니다.**

검증할 방법이 없었기 때문입니다. 가진 것은 제가 그린 합성 얼굴뿐인데, 이 얼굴은
평면 음영에 눈두덩·코 그림자가 없고 공막이 과하게 밝습니다. 실제로 어두운 피부톤
합성 얼굴에서는 **정답 위치(-0.42)가 30% 밀린 위치(0.20)보다 낮은 점수**를
받았습니다. 이걸 통과시키려면 합성 생성기가 제 검출기를 만족하도록 얼굴을 다시
그려야 하는데, 그건 검증이 아니라 순환논법입니다. 가중치를 손으로 고른 검증기를
합성 데이터로만 확인하고 신뢰도 신호로 쓰는 것은 정확히 이 문서가 경계하는
과장입니다. 코드째 삭제했습니다.
### 비교형 진단 (구현 완료)

이 도구에서 **유일하게 모델이 아닌 사람이 답을 내는** 부분입니다.

오프라인 진단은 "이 사람은 웜인가"를 절대적으로 판정하지 않습니다. 천을 번갈아
대보고 **둘 중 어느 쪽이 나은가**를 묻습니다. 사람의 눈은 절대 색을 재는 데는
약하지만 두 상태를 비교하는 데는 대단히 강하기 때문입니다. 우리 엔진은 정확히
반대입니다 — 픽셀 값은 정확히 읽지만, 그 값의 기준선은 개발자가 정한 휴리스틱입니다.

그래서 둘을 합칩니다. 축마다 2문항씩 6문항, 각 문항은 **한 축만** 다른 색 쌍을
얼굴에 직접 대봅니다 (아이보리↔순백, 골드↔실버, 파우더핑크↔버건디, 라이트아쿠아↔딥틸,
비비드레드↔더스티로즈, 로열블루↔슬레이트블루).

| 결과 | 처리 |
|---|---|
| 세 축 모두 일치 | 사진 계산과 당신의 눈, **두 가지 근거**를 가진 결과 |
| 한 축 갈림 (타입 불변) | 그 축이 경계에 있다고 표시 |
| 한 축 갈림 (타입 변함) | 보정 타입을 함께 제시 — 예: 봄 스트롱 ↔ **여름 브라이트** |
| 두 축 이상 갈림 | 사진 색이 잘못 잡혔을 가능성. **당신 눈을 기준으로** 안내 |

충돌한 축은 사용자 방향으로 뒤집되, 크기는 모델이 스스로 가졌던 확신을 반대편에
그대로 옮깁니다(최소 0.35). ±1로 밀지 않는 이유는 사용자가 "어느 쪽이 낫다"고
답한 것이지 "극단이다"라고 답한 것이 아니기 때문입니다.

> **자동 판정을 조용히 덮어쓰지 않습니다.** 두 답을 나란히 보여주고 무엇이
> 어긋났는지 말합니다. 어긋남 자체가 사용자에게 가장 쓸모 있는 정보입니다.

### 하이브리드 체형 (구현 완료)

사진에서 재는 것은 **실루엣의 폭**이고 줄자로 재는 것은 **둘레**입니다. 둘은 같은
값이 아닙니다. 폭에서 둘레를 얻으려면 몸의 단면을 타원으로 가정해야 하는데 그
가정이 사람마다 크게 다릅니다. 그래서 **둘을 변환하지 않습니다.** 각자의 방식으로
따로 판정하고 대조만 합니다.

- **실측 판정** — 가슴·허리·엉덩이 둘레로 공개 기준(FFIT, Simmons et al. 2004)의
  단순화 버전을 적용합니다. 임계값(가슴−허리 23cm, 엉덩이−허리 25cm, 균형 5cm)은
  우리가 고른 값이 아니라 **인용한 값**입니다.
- **키 검산** — 키 ÷ 등신 = 머리 길이. 성인 범위(약 21~26cm)를 벗어나면 사진에서
  정수리나 발끝을 잘못 잡은 것입니다. 이 검산은 사진 판정을 고치지 않고 틀렸다는
  사실만 알려줍니다.
- **어긋나면 줄자가 이깁니다.** 실측은 관측이고 사진 판정은 추정입니다.

> 남성·공용은 모래시계 판정을 하지 않습니다. 위 드롭 임계값은 여성복 사이징
> 연구에서 나온 값이라 남성 체형에 그대로 쓸 근거가 없습니다. 없는 근거로
> 판정하느니 그 항목을 비워 둡니다.


### 다음에 해야 할 일 (우선순위)

```
P1  검출 개선     색 기반 피부 마스크 → 얼굴 랜드마크·인물 분할 모델 (아래 참고)
P2  검증 데이터   피부톤·기종·조명별 테스트 세트 + 전문가 2~3인 독립 라벨 + 합의/경계 라벨
P3  측면 사진     ✅ 구현 — 옆모습 2장으로 앞뒤 두께 측정 (docs/07)
                  남은 것: 잰 두께를 핏 성향(스트레이트/웨이브/내추럴) 판정에 반영
P4  옷 데이터     사용자 반입 외에 재배포 가능한 상품컷 확보 (라이선스 문제)
```

> **P2 검증 데이터는 코드로 풀 수 없는 유일한 항목입니다.** 실제 사람의 사진과
> 전문가 라벨이 필요하고, 그건 개발이 아니라 데이터 수집·동의·보상의 문제입니다.
> 이것이 없는 한 12타입 자동 판정의 정확도는 계속 "검증 전"으로 남습니다.
> 지금까지 한 일은 전부 그 공백을 메우는 대신 **공백을 정직하게 드러내는** 쪽이었습니다
> — 재현성 측정, 촬영 표준화, 얼굴 위치 교차검증, 비교형 진단, 실측 검산.

> **P1 검출 개선이 왜 아직 열려 있는가.** 얼굴 랜드마크·인물 분할 모델을 쓰려면
> 모델 가중치 파일이 필요합니다. 이 도구의 배포 형태는 *더블클릭으로 열리는 단일
> HTML 400KB*이고 그것이 "사진이 브라우저 밖으로 나가지 않는다"는 약속의 근거이기도
> 합니다. 여기에 2MB+ 모델을 넣거나 CDN에서 받아오면 오프라인 실행과 배포 단순성이
> 함께 깨집니다. 브라우저 기본 `FaceDetector`(Shape Detection API)는 아직 어느
> 브라우저에서도 실제로 쓸 수 없습니다.
>
> 그래서 **모델 교체는 미뤄 두고, 교체로 막으려던 실패를 먼저 드러내게 했습니다**
> (위 *얼굴 위치 교차검증*). 오검출을 없앤 것이 아니라, 오검출이 조용히 지나가지
> 못하게 만든 것입니다. 모델 교체는 배포 형태를 바꾸기로 결정한 뒤에 할 일입니다.

## 윤리 기준

- 외모 점수·미모 등급·인종 추정을 **출력하지 않습니다.**
- ITA°는 피부과 명도 지표로만 쓰며 인종 판정에 사용하지 않습니다.
- "감추세요" 대신 "이 실루엣이 이렇게 보이게 합니다"로 서술합니다.
- 얼굴 이미지는 개인정보보호법상 민감정보입니다. 기본 처리는 온디바이스이며,
  저장하는 것은 이미지가 아니라 추출된 수치뿐입니다.
- 결과는 참고용이며 최종 판단은 사용자와 전문가에게 있습니다.
