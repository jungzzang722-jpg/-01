# 고화질 합성 API — 설계

## 왜 하는가

내장 엔진은 평면 옷본을 실루엣에 맞춰 휘어 붙입니다. 천이 몸에 감기는 느낌,
주름이 지는 방향, 팔이 옷을 가리는 관계 — 이런 것들은 **그 방식에 없습니다.**
버그를 다 잡아도 생기지 않습니다. 확산 모델 기반 가상 피팅은 그것을 학습으로
알고 있고, 격차는 조정으로 좁혀지지 않습니다.

동시에 이 앱의 약속은 "사진이 브라우저 밖으로 나가지 않는다"입니다. 그래서
**한 파일 안에서 두 가지를 다 하지 않습니다.**

---

## 1. 파일을 둘로 나눈다

```
퍼스널컬러진단.html              원본 — 네트워크 코드가 한 줄도 없다
퍼스널컬러진단_고화질합성.html    원본 + vton.js
```

`build/build.py` 가 두 벌을 함께 만듭니다. 손으로 두 파일을 관리하면 한쪽만
고쳐지는 것은 시간문제입니다.

원본의 불변식은 테스트로 못 박혀 있습니다 (`build/test-vton.mjs`):

| 검사 | 원본 | 고화질판 |
|---|---|---|
| `fetch(` | 없음 | 있음 |
| `XMLHttpRequest` · `WebSocket` · `sendBeacon` · `EventSource` | 없음 | — |
| `global.VTON` | 없음 | 있음 |

원본에서 사이드바의 방패와 "이 브라우저 밖으로 나가지 않습니다"는
**무조건 참**입니다.

---

## 2. API 키는 클라이언트에 둘 수 없다

이 앱은 더블클릭으로 열리는 HTML 한 개입니다. 거기에 키를 넣으면 **파일을
받은 사람 누구나 키를 꺼내 쓸 수 있습니다.** 난독화는 해결이 아닙니다.

그래서 작은 중계 서버가 반드시 필요합니다.

```
브라우저 (고화질판)  ──►  중계 서버  ──►  공급자 API
   주소만 안다            키를 든다        모델이 산다
```

`server/vton-proxy.mjs` — **의존성 없음**, Node 18+ 내장 `http` 와 `fetch` 만
씁니다.

```
VTON_API_KEY=... VTON_PROVIDER=replicate VTON_MODEL=<버전> node server/vton-proxy.mjs
```

주소를 넣지 않으면 기능이 통째로 꺼지고, 그때 고화질판은 원본과 똑같이
동작합니다. 이것이 기본 상태입니다.

---

## 3. 무엇이 나가는가

**나가는 것**
- **배경을 지운 전신 인물** PNG (최대 변 1024px). 분리는 이미 온디바이스에서
  끝나 있으므로(`SEGMENT.person`) 그 결과를 재사용합니다. 방·가구·같이 있는
  사람은 나가지 않습니다.
- 옷 이미지 (최대 변 768px)
- 부위(top/bottom)와 옷 이름

**나가지 않는 것**
- **1단계의 얼굴 진단 사진** — 절대 보내지 않습니다
- 원본 배경
- 진단 결과·측정값·개인 설정

**얼굴은 나갑니다.** 얼굴을 지우면 모델이 사람을 그리지 못합니다. 지우는
대신 그 사실을 동의 문구에 그대로 적습니다.

테스트가 이를 검사합니다 — 보내는 이미지의 네 모서리가 투명한지, 인물이
차지하는 면적이 정상 범위인지.

---

## 4. 색 진단은 생성 이미지를 쓰지 않는다

이것이 이 앱 특유의 함정입니다. 퍼스널 컬러 진단은 사진에서 **잰** 피부·모발·
홍채 색이 전부입니다. 이미지 모델은 사람을 다시 그리므로 그 색이 바뀝니다.

생성된 이미지로 진단하면 "당신은 겨울 딥"이라고 말한 얼굴과 화면 속 얼굴의
색이 달라져 **서비스가 스스로 모순됩니다.**

그래서 경계가 이렇습니다.

```
진단 (1·2단계)  ─── 온디바이스 전용, 원본 사진에서 측정
피팅 (3단계)    ─── 여기서만 외부 호출, 결과는 보기용
```

---

## 5. 겹쳐 입기는 한 벌씩

확산 모델은 **옷 한 벌을 입히는 것**으로 학습돼 있습니다. 여러 벌을 한 번에
주면 섞어 그립니다. 그래서 아래층부터 한 벌씩 순서대로 입히고, 이전 결과를
다음 호출의 인물로 넘깁니다.

이 왕복은 **서버 안에서** 처리합니다. 클라이언트가 매번 큰 이미지를 다시
올리면 지연이 배로 늘기 때문입니다.

---

## 6. 캐시

장당 과금이고 한 번에 10~30초가 걸립니다. 슬라이더를 만지거나 탭을 오갈
때마다 다시 부르면 비용도 체감 속도도 무너집니다.

사람과 옷 조합이 같으면 결과도 같으므로, `hash(인물) + 옷 목록`을 키로
IndexedDB 에 저장합니다. 실측에서 재호출이 **204ms → 6ms**, 그리고 그 사이에
아무것도 전송되지 않습니다.

---

## 7. 공급자는 갈아 끼울 수 있어야 한다

이 분야는 6개월이면 더 나은 것이 나옵니다. 어댑터는 `(인물 PNG, 옷 PNG,
작업정보) → PNG` 하나만 맞추면 됩니다.

| 공급자 | 옷 충실도 | 인물 보존 | 사진이 나가는가 | 비고 |
|---|---|---|---|---|
| 전용 VTON 모델 (호스팅) | 높음 | 높음 | 나감 | 이 작업만 학습돼 있다 |
| 범용 이미지 편집 모델 | **약함** | 중간 | 나감 | 고른 옷이 아닌 비슷한 옷을 그릴 수 있다 |
| 직접 구동 (IDM-VTON 등) | 높음 | 높음 | **안 나감** | GPU 서버 필요, 이 앱의 약속에 가장 가깝다 |

**"정확히 그 옷"을 보여줘야 하는 서비스**라는 점이 선택을 가릅니다. 코디
추천에서 다른 옷이 그려지는 것은 치명적입니다.

> ⚠ 모델 이름·엔드포인트·단가는 공급자마다 다르고 자주 바뀝니다. 코드에
> 박아 두지 않고 환경변수로 뺐습니다. **현재 문서에서 확인해** 넣어야 합니다.

---

## 8. 실패하면 어떻게 되는가

고화질 합성은 **덤**입니다. 실패해도 앱은 그대로 동작해야 합니다.

| 상황 | 동작 |
|---|---|
| 주소 미설정 | 기능이 꺼진 상태 — 원본과 동일 |
| 동의 안 함 | 전송하지 않음 |
| 서버 연결 실패 | 내장 엔진 결과를 그대로 쓰고 이유를 표시 |
| 키 거부(401/403) | "중계 서버의 키 설정을 확인해 주세요" |
| 한도 초과(429) | "잠시 후 다시 시도해 주세요" |
| 90초 초과 | 중단하고 내장 엔진 결과 유지 |

상태 코드만 보여주면 아무도 못 고치므로 사용자의 말로 옮깁니다.

---

## 9. 화면

피팅 탭 아래에 카드 하나가 붙습니다. `fitroom.js` 는 건드리지 않습니다 —
두 파일이 공유하는 코드라 거기에 넣으면 원본에도 따라 들어갑니다. 대신
패널이 나타나는 것을 지켜보다 스스로 끼어듭니다.

결과는 **나란히** 보여줍니다.

```
[ 내장 엔진 ]        [ 고화질 ]
즉시 · 사진 안 나감   10~30초 · 사진 나감
```

무엇을 얻고 무엇을 내주는지가 한눈에 보여야 사용자가 선택할 수 있습니다.

---

## 아직 정하지 않은 것

- **공급자 선택.** 위 표의 트레이드오프는 정리했지만 실제 단가·품질은
  후보 2~3곳에 같은 사진을 넣어보고 정해야 합니다.
- **배포 형태.** 중계 서버를 사용자가 직접 띄우는지(로컬), 서비스로 띄우는지
  (호스팅). 코드는 양쪽 다 되지만, 호스팅하면 "사진이 우리 서버를 거친다"가
  되므로 개인정보 처리방침이 필요합니다.
- **한도.** 장당 과금이므로 사용자당·시간당 상한이 필요합니다. 지금은 없습니다.
